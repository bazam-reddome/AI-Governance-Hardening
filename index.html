Five flows on one page.

The kit's operating model in pictures, in the order the story flows: where AI tools live (endpoint), how they're contained (policy-as-code hardening), how the apps they build get to production (SDLC), where those apps live during validation (sandbox), and the per-request guardrails for LLM features inside them. AI-built app sandbox — Stage 5 detail

Three deployment patterns · isolated by default

Where an AI-built application lives between Stage 4 (security review) and Stage 6 (production). Three deployment patterns are shipped in templates/sandbox/ — pick the one that fits your stack. All three share the same boundary controls: SSO at the front door, deny-by-default egress, synthetic test data only, full request logging to SIEM, time-bounded lifetime. The exit is two-way: approved goes to production with a re-signed image, rejected goes back to the developer with a remediation list.

Endpoint & SDLC

Contain AI coding tools on the metal — then promote what they build.

Two operational layers most starter kits skip. The Endpoint Hardening Profile enforces Claude Code via the published managed-settings.json policy and contains the rest (Codex, Copilot CLI, Cursor, ChatGPT desktop) at the OS layer — TCC on macOS, AppLocker on Windows, firejail on Linux — plus a deny-by-default proxy egress policy applied at your SSE / corporate proxy. The CI / sandbox bundle then gates anything they produce through SAST, SBOM, signing, an isolated sandbox, and a security review before it reaches prod.

Step-by-step guides

Walk through it. Don't read a 30-page doc.

Three guided flows. The first protects every developer endpoint with an enforced policy via Microsoft Intune; the second stands up the isolated sandbox an AI-built application lives in during Stage 5; the third runs every AI-built application through the six-stage promotion path before it reaches production. Pick a tab, follow the numbered steps, tick off as you go.

Note on Intune navigation: Microsoft refreshes the Intune admin centre and the Microsoft Defender XDR portal frequently. Menu paths quoted below reflect the layout at the time of writing — feature names are the stable signal, not the breadcrumbs. If a path doesn't match what you see in your tenant, use the portal's top search box, then verify against the current Microsoft Learn documentation before deploying.

Protect endpoint for safe usage of AI tools

Microsoft Intune · macOS & Windows 11

  1. Generate the policy artefacts

    Clone or download this project. Tailor templates/endpoint-policy/policy.yaml with your organisation's allow-lists, then validate and emit:

    cd templates/endpoint-policy && pip install pyyaml jsonschema && python3 emit.py

    You'll get an out/macos/aigov-tcc.mobileconfig, an out/claude/managed-settings.json + managed-mcp.json, and an out/common/policy.json for the pre-flight script.

    ↓ policy.yaml  ·  ↓ emit.py

  2. Provision a dedicated APFS sandbox volume on every Mac

    Intune doesn't create APFS volumes natively, so deploy a one-shot shell script.

    Intune: Devices → Scripts and remediations → Add → macOS → Shell script

    Upload a script that resolves the boot APFS container (Apple Silicon Macs are not always on disk1) then adds the volume:

    CONTAINER=$(diskutil apfs list | awk '/Container Reference:/ {print $NF; exit}'); diskutil apfs addVolume "$CONTAINER" APFS AIWorkspaces -size 100G

    Then create the working folder at /Volumes/AIWorkspaces/ai-workspaces. Set "Run script as signed-in user = No"; "Hide notifications = Yes"; assign to your developer device group.

    • Verification: on a target Mac, diskutil list shows the new APFS volume.

  3. Push the TCC configuration profile

    This denies AI desktop apps access to Documents, Desktop, Downloads, and the rest of the home directory — they may only see the sandbox volume.

    Intune: Devices → Configuration → Create profile → macOS → Templates → Custom

    Open aigov-tcc.mobileconfig: replace each __REPLACE_WITH_CODESIGN_DESIGNATED_REQUIREMENT__ placeholder with the actual designated requirement string captured via codesign -dr - /Applications/Claude.app. Verify each bundle ID against your fleet (use mdls -name kMDItemCFBundleIdentifier /Applications/<App>.app). macOS 11+ silently ignores TCC entries lacking a valid CodeRequirement. Assign to the developer device group.

    • Verification (correct method): on a target Mac, drag a file from ~/Documents into Claude — Claude shows a Finder access denial. Or run log stream --predicate 'subsystem == "com.apple.TCC"' to observe denials in real time.

  4. Deploy Claude Code managed-settings.json

    Pushes the file, MCP and network policies you defined in YAML into the machine-wide path Claude Code's enterprise policy reads. Note: Claude Desktop uses a different mechanism — OS-level controls (the TCC profile in step 3 + the proxy in step 5) govern it.

    Intune: Devices → Scripts and remediations → Add → macOS → Shell script

    Upload a script that copies managed-settings.json to /Library/Application Support/ClaudeCode/managed-settings.json with permissions 0644, owner root:wheel. Set "Run script as signed-in user = No"; assign to the developer device group.

    • Verification: sudo cat "/Library/Application Support/ClaudeCode/managed-settings.json" on a target Mac.
    • Verify field names against Anthropic's current Claude Code enterprise policy docs before broad rollout.

  5. Force outbound traffic through the corporate proxy

    Configures system-wide proxy so AI tools can only reach the allow-listed model APIs and registries.

    Intune: Devices → Configuration → Create profile → macOS → Settings catalog → search "proxy" — configure HTTP / HTTPS global proxy. For tenants without the settings catalog version, use macOS → Templates → Custom and upload a global proxy .mobileconfig with payload type com.apple.proxies.http.global.

    Set the auto-config URL or static proxy + port to point at your SSE / Zscaler / Squid. Apply the egress allow-list (out/windows/network-allow-list.txt works for any proxy that takes a flat list) on the proxy itself.

  6. Schedule the pre-flight script as a launchd job

    Verifies on every login + every 24h that the policy is in force, posts JSON to your SIEM.

    Intune: Devices → Scripts and remediations → Add → macOS → Shell script

    Upload a script that drops aigov-preflight.sh to /usr/local/bin/ and writes a launchd .plist at /Library/LaunchAgents/com.aigov.preflight.plist running every 86400 seconds.

    ↓ aigov-preflight.sh

  7. Verify on a test device

    Run the pre-flight by hand on a freshly-enrolled Mac:

    /usr/local/bin/aigov-preflight.sh --webhook https://siem.your-org.com/ingest/aigov

    You should see all checks pass. The same JSON should land in your SIEM.

    • If any check fails, fix it before rolling out widely. Test cohort first; production cohort last.

  1. Generate the policy artefacts

    Same as macOS step 1 — run emit.py after tailoring policy.yaml. You'll get out/windows/applocker.xml, out/windows/network-allow-list.txt, out/claude/managed-settings.json + managed-mcp.json, and out/common/policy.json.

    ↓ policy.yaml  ·  ↓ emit.py

  2. Provision a Windows 11 Dev Drive on every endpoint

    Dev Drive (ReFS) provides the trusted boundary for AI working folders and gives developers measurable performance gains as a bonus.

    Intune: Devices → Scripts and remediations → Add → Windows 10 and later → PowerShell script

    Upload a script that runs New-VHD + Mount-VHD + Initialize-Disk + New-Partition + Format-Volume -FileSystem ReFS -DevDrive creating D:\ai-workspaces. Then configure the Dev Drive antivirus filter list — the exact filter names depend on the AV / EDR you run (e.g. WdFilter for Microsoft Defender, MsSense.sys for Defender for Endpoint). Use fsutil devdrv setfiltered <comma-separated-filter-list>; verify the current filter names against the Microsoft Learn Dev Drive docs before deploying. Without this step, Dev Drive's perf and security promises aren't realised. Run as system; 64-bit; assign to the developer device group.

    • Requires Windows 11 22H2 or later. Verify with Get-Volume | ? FileSystemType -eq ReFS and fsutil devdrv query D:.

  3. Deploy the AppLocker policy

    Restricts AI executables to the Dev Drive and denies them on system / personal locations.

    Intune: Devices → Configuration → Create profile → Windows 10 and later → Templates → Custom

    Add an OMA-URI setting:

    • OMA-URI: ./Vendor/MSFT/AppLocker/ApplicationLaunchRestrictions/AIGov/EXE/Policy
    • Data type: String
    • Value: paste the inner RuleCollection XML from applocker.xml for the Exe rule collection (matching Microsoft's CSP schema).

    Repeat for Script (use EnforcementMode = AuditOnly during pilot, flip once telemetry is clean). Note: Intune's Endpoint security → Application control for Business blade uses the WDAC schema, not AppLocker — push AppLocker through the Custom OMA-URI route.

    • Verification: try to launch an AI tool from %USERPROFILE%\Documents — Windows blocks it; AppLocker event log under Microsoft-Windows-AppLocker / EXE and DLL shows the deny.

  4. Enable Defender ASR rules

    Stops the secondary attack surface that AI tool compromise typically pivots through.

    Intune: Endpoint security → Attack surface reduction → Create policy → Windows 10/11 → Attack surface reduction rules

    Enable the following at Block:

    • Block credential stealing from lsass (9E6C4E1F-7D60-472F-BA1A-A39EF669E4B2)
    • Block process creations from PSExec and WMI (D1E49AAC-8F56-4280-B9BA-993A6D77406C)
    • Block executable content from email and webmail (BE9BA2D9-53EA-4CDC-84E5-9B1EEEE46550)
    • Block untrusted and unsigned processes from running from USB (B2B3F03D-6A65-4F7B-A9C7-1C7EF74A9BA4)

  5. Push the network egress allow-list

    The primary egress control should be your corporate proxy / Secure Service Edge — Zscaler, Netskope, Cloudflare Gateway, Squid, or equivalent. Apply the allow-list there. Intune doesn't natively do URL allow-listing well; use it to force traffic through the proxy.

    Force-proxy on Windows endpoints: the most reliable approach in 2026 is the corporate SSE / proxy agent itself (Zscaler Client Connector, Netskope Client, Cloudflare WARP). For Intune-only setups, configure a system-wide proxy via the Intune Settings catalog (search 'proxy' when authoring a Windows 10/11 configuration profile) — verify the exact setting names against the current Microsoft Learn documentation, since the catalog refreshes regularly.

    Optional complementary control — Microsoft Defender Web Content Filtering: configure URL category / domain blocking in the Microsoft Defender portal at security.microsoft.com → Endpoints → Rules → Web content filtering. Note: requires Microsoft Defender for Endpoint P1 or P2 licence and only enforces on Edge / Chrome on managed devices. This is not a substitute for the corporate proxy.

    ↓ policy.yaml contains the canonical allow-list; the emit step produces network-allow-list.txt in a flat format most proxies accept.

  6. Deploy Claude Code managed-settings.json

    Pushes the file, MCP and network policies into the machine-wide Claude Code policy path. Note: Claude Desktop uses a different mechanism — OS-level controls (AppLocker + the proxy) govern it.

    Intune: Devices → Scripts and remediations → Add → Windows 10 and later → PowerShell script

    Upload a script that copies managed-settings.json to C:\ProgramData\ClaudeCode\managed-settings.json (machine-wide). Run as: System; 64-bit.

    • Verification: Get-Content "$env:ProgramData\ClaudeCode\managed-settings.json" on a target endpoint.
    • Verify field names against Anthropic's current Claude Code enterprise policy docs before broad rollout.

  7. Schedule the pre-flight as a remediation

    Runs on login + every 24h, posts JSON to SIEM, returns exit code 0/1/2 so Intune surfaces health on the device-compliance dashboard.

    Intune: Devices → Scripts and remediations → switch to the Remediations tab → Create. (The Remediations tab is a sibling of the Platform scripts tab, not nested below it.)

    Detection script: aigov-preflight.ps1 -Quiet -Webhook <your-siem>. Remediation script: empty (or trigger a re-deploy of the configs). Schedule: hourly during business hours, daily otherwise.

    ↓ aigov-preflight.ps1

  8. Verify on a test device

    From an elevated PowerShell on a freshly-enrolled Windows endpoint:

    .\aigov-preflight.ps1 -Webhook https://siem.your-org.com/ingest/aigov

    Confirm: AppLocker service running, Dev Drive present, ASR rules configured, Claude managed-settings.json present, BitLocker on, no risky env vars, no AI processes running yet. Same JSON should appear in SIEM.

Stand up the AI-built app sandbox

three patterns · Cloudflare · Docker · Kubernetes

  1. Step 1 — Prerequisites

    Owner: Platform Engineering.  Exit: Cloudflare Workers paid plan + Access on the zone, plus the build artefact already cosign-signed by Stage 3 of the SDLC.

    Confirm Cloudflare account has Workers (paid), Access (Zero Trust), and the relevant resource bindings you need (D1 / R2 / KV). Identity provider hooked into Access via SAML / OIDC. wrangler CLI installed locally (npm install -g wrangler) and authenticated against the production-isolated tenant (not your prod tenant).

  2. Step 2 — Customise wrangler.toml

    Exit: tokens replaced; wrangler deploy --dry-run succeeds.

    Use the Customisation Wizard above with the Sandbox tenant slug and Sandbox owner email fields filled, or replace [REPLACE_WITH_TENANT_SLUG] and [REPLACE_WITH_OWNER_EMAIL] manually. Verify each [[d1_databases]] / [[r2_buckets]] / [[kv_namespaces]] entry references the sandbox-only resources, not production. The [triggers] cron entry tears the deployment down at 14 days — leave it on.

    ↓ wrangler.toml

  3. Step 3 — Cloudflare Access policy

    Exit: only security-reviewers SSO group can reach the sandbox URL.

    In the Cloudflare Zero Trust dashboard → Access → Applications → Add an application. Bind to the sandbox subdomain. Add a single Allow rule: SSO group is security-reviewers AND device posture is compliant AND MFA is enabled. Block everything else. Add session duration ≤ 8 hours. Log all access events to your SIEM via the Cloudflare Logpush job.

  4. Step 4 — Deploy + verify

    Exit: sandbox URL responding only to authorised SSO sessions; logs flowing to SIEM.

    Run wrangler deploy. Visit the sandbox URL from a non-corporate browser to confirm the Access challenge fires. Visit it after authenticating to confirm the app responds. In SIEM, confirm cf-access events for both attempts. Tag the deployment with the PR number and the cosign signature digest for traceability.

  5. Step 5 — Hand off to security review

    Exit: security reviewer has the URL, the SBOM, and the cosign attestation.

    Post in the PR: sandbox URL · cosign signature · CycloneDX SBOM (with AI/ML extension) · evaluation harness output (if applicable). Stage 4 (security review) of the Promotion Runbook starts here.

    ↓ Promotion Runbook (Stage 4 sign-off form)

  1. Step 1 — Prerequisites

    Owner: Platform Engineering.  Exit: isolated host with Docker 24+, kernel 5.8+ (for capability-based hardening), reachable only from the corporate VPN.

    Provision a dedicated VM in a non-production VPC. Apply your standard Linux baseline. Install Docker Engine + Compose v2. Confirm docker compose version reports 2.20+. Open inbound 443 from the corporate VPN range only. Outbound: only the corporate proxy.

  2. Step 2 — Customise docker-compose.yml

    Exit: docker compose config validates; capabilities and networks match the policy.

    Open the shipped docker-compose.yml. Verify the AI-app service has read_only: true, cap_drop: [ALL], security_opt: [no-new-privileges:true], tmpfs: [/tmp]. Verify the tinyproxy egress firewall is on the only network with internet, and the AI app sits on a network with internal: true. Adjust the egress allow-list inside tinyproxy.conf to your model API + needed registries only.

    ↓ docker-compose.yml

  3. Step 3 — Build the hardened image

    Exit: image built from the kit's hardened Dockerfile, distroless, non-root, cosign-signed.

    Use Dockerfile.template as the basis. Multi-stage; final stage gcr.io/distroless/python3-debian12:nonroot (or the equivalent for your runtime). UID 65532. HEALTHCHECK calls the runtime directly, not a shell. Build, push to your registry, sign with cosign sign --yes <ref>. Attach the CycloneDX SBOM with the AI/ML extension as a cosign attestation.

    ↓ Dockerfile.template

  4. Step 4 — Stand up OAuth2-Proxy in front

    Exit: sandbox URL gated by SSO; only security-reviewers group can reach the AI app.

    Deploy oauth2-proxy as the front door (already wired into the compose file). Bind to your IdP via OIDC. Redirect URI on the sandbox host. Allowed group: security-reviewers. Audit log forwarded to your SIEM via Vector / Fluent Bit (also already in the compose).

  5. Step 5 — Bring it up + verify

    Exit: Falco is observing, egress is bounded, the app is reachable only via SSO.

    Run docker compose up -d. From a non-VPN host: confirm 401. From a VPN-connected, SSO-authenticated browser: confirm the app responds. Trigger a deliberate egress to a non-allow-listed URL from inside the AI container — confirm tinyproxy denies it AND Falco fires an event in your SIEM. Schedule a 14-day teardown via cron / systemd timer.

  6. Step 6 — Hand off to security review

    Exit: security reviewer has the URL, the cosign-signed image reference, the SBOM, and the eval-harness output.

    Same hand-off as the other patterns — Stage 4 of the Promotion Runbook starts here.

    ↓ Promotion Runbook (Stage 4 sign-off form)

  1. Step 1 — Prerequisites

    Owner: Platform Engineering.  Exit: non-production cluster, NetworkPolicy-enforcing CNI (Cilium / Calico), Kyverno installed.

    Use a sandbox-tier cluster (separate from production). Confirm the CNI enforces NetworkPolicy by deploying a default-deny test pod. Install Kyverno: helm repo add kyverno https://kyverno.github.io/kyverno/ && helm install kyverno kyverno/kyverno -n kyverno --create-namespace. Cluster admin access required for the policy step.

  2. Step 2 — Apply Kyverno cluster policies

    Exit: 5 cluster policies enforced; cosign signature verification active.

    Apply the shipped kyverno-policies.yaml: verify image signatures (cosign keyless against your CI's OIDC subject), deny privileged / host-namespaces / default-SA, require resource limits + non-root + read-only-root, require image digests, harden the default ServiceAccount. Stage-roll the policies as Audit first if you have legacy workloads, then flip to Enforce.

    ↓ kyverno-policies.yaml

  3. Step 3 — Customise the Deployment + ServiceAccount + PDB

    Exit: namespace + dedicated SA + Deployment exist; PSS-restricted enforced.

    Open k8s/deployment.yaml. Replace <your-app>, <your-namespace>, <your-org>, and the @sha256:<DIGEST> of your cosign-signed image. Confirm the namespace label pod-security.kubernetes.io/enforce: restricted is present. Confirm automountServiceAccountToken: false on the SA. Apply.

    ↓ deployment.yaml

  4. Step 4 — Apply NetworkPolicy

    Exit: default-deny on, only DNS + ingress controller + model API egress allowed.

    Apply networkpolicy.yaml. Confirm a curl from inside the pod to 1.1.1.1:443 succeeds (model API range), and to 10.0.0.5:6379 fails (other in-cluster service). DNS resolution to kube-dns works; everything else inside the cluster is unreachable until you explicitly allow it.

    ↓ networkpolicy.yaml

  5. Step 5 — SSO at the edge

    Exit: Ingress only via the cluster's authenticating gateway; only security-reviewers group can reach the sandbox URL.

    Use your existing Ingress controller / service mesh (oauth2-proxy on ingress-nginx, Istio AuthZ, or your IdP-integrated gateway). Bind to the sandbox hostname. Allowed group: security-reviewers. The NetworkPolicy in Step 4 already allows ingress from the gateway namespace only.

  6. Step 6 — Verify admission + runtime

    Exit: a tag-only or unsigned image is rejected at admission; runtime detection fires on policy violations.

    Try kubectl run bad --image=ghcr.io/<your-org>/<your-app>:latest — must fail (digest required, signature not present). Try kubectl run privileged --image=<valid> --privileged — must fail. If you've added Falco / Tetragon (recommended), confirm runtime alerts reach your SIEM. Schedule a TTL-based cleanup of the namespace at 14 days.

    Exit: security reviewer has the URL, the signed image digest, the SBOM, and the Kyverno admission audit trail.

    Same hand-off as the other patterns — Stage 4 of the Promotion Runbook starts here.

Promote AI-built apps safely (SDLC)

six stages · NIST SSDF + SLSA L3

  1. Stage 0 — Generation

    Owner: Developer.  Exit: code lands in a feature branch with AI co-author markers.

    Author works inside the AI working folder enforced by the endpoint policy. AI tool's MCP allow-list, plugin allow-list, and egress controls are in force (verified by pre-flight on login). Commits include the AI co-author marker and preserve the prompt(s) used as a comment block at the top of the PR description.

  2. Stage 1 — Self-review

    Owner: Developer.  Exit: PR opened with self-review checklist completed and AI provenance documented.

    Walk the entire diff. Read every AI-added line. Look for the predictable failure modes: hardcoded secrets, missing input validation, broken error handling, weak auth/authz checks, dependency hijacking, AI-suggested package names that don't exist (slop-squatting), tautological tests.

    ↓ Code Review Checklist (use sections 1–8 here)

  3. Stage 2 — Pre-merge gates (CI + peer review)

    Owner: CI runner + named human reviewer(s).  Exit: all required CI checks green AND peer-review approval(s) recorded → PR merges to main.

    Automated half (CI): Drop the pre-commit pack at the root of every dev repo, and the GitHub Actions workflow at .github/workflows/ai-app-gates.yml. Branch protection requires every gate to pass: gitleaks + trufflehog (secrets), Semgrep with the AI-rules pack (SAST), OSV-Scanner (deps), ScanCode (licence), Trivy (container, when a Dockerfile is present), Anchore sbom-action / Syft → CycloneDX with structured ML metadata (SBOM), SLSA L3 provenance, cosign keyless signing.

    Human half (peer review): branch protection on main requires at least one approving human reviewer (recommend two for changes >50 LoC or that touch security-sensitive paths). CODEOWNERS approval is required for the affected paths. Stale approvals are dismissed on new commits. Auto-merge is disabled. AI-authored PRs (detected by the co-author marker) are flagged for senior reviewer.

    ↓ pre-commit pack  ·  ↓ GitHub Actions workflow

  4. Stage 3 — Sandbox deploy

    Owner: Platform Engineering.  Exit: sandbox URL live, SSO-gated, logs flowing.

    Deploy the artefact to an isolated sandbox tenant. Two reference architectures ship with this kit. Cloudflare-native: wrangler deploy with the included wrangler.toml + a Cloudflare Access policy in the Zero Trust dashboard requiring the security-reviewers SSO group + compliant device + MFA. Self-hosted: docker compose up -d with the included compose file (OAuth2-Proxy + Vector + Falco). Sandbox carries no production data; egress firewalled to model APIs only; auto-expires after 14 days.

    ↓ wrangler.toml (Cloudflare)  ·  ↓ docker-compose.yml (self-hosted)

  5. Stage 4 — Security review

    Owner: Security Engineering.  Exit: checklist complete; High/Critical findings closed or risk-accepted.

    Reviewer runs the AI Code Review Checklist (all 10 sections). Pen-tests the sandbox URL: auth bypass, IDOR, SSRF, prompt injection (if LLM exposed), excessive agency on agent endpoints. Verifies SBOM and cosign signature. Findings raised in the issue tracker tied to the PR; High/Critical findings closed or formally risk-accepted before sign-off.

    ↓ Code Review Checklist (full)

  6. Stage 5 — Promotion sign-off

    Owner: Security Manager + Product Manager + Engineering Manager.  Exit: three signatures in the Decision Log.

    Decision Log entry created with the evidence pack (CI run URL, SBOM, SLSA provenance, sandbox URL, security review checklist, reviewer summary). Three named approvers sign. Expiry date set (default 12 months). Configure your production admission controller (Kyverno / OPA Gatekeeper / Sigstore policy-controller — not shipped with this kit) to verify cosign signatures before allowing deploy.

    ↓ Promotion Runbook (Appendix C — Sign-off form)

  7. Stage 6 — Production deploy

    Owner: SRE / Platform.  Exit: post-deploy review filed, oncall briefed.

    Canary stages 1% → 10% → 50% → 100%. Configure auto-rollback in your deployment platform on the signals you care about (typical: 5xx rate, p95 latency, custom AI-quality KPIs). Observability flowing with the AI-app tag. On-call runbook updated. Post-deploy review at 24h and 7d. Re-evaluation scheduled at 90 days for AI-specific drift.

Why this matters

The risks that traditional security controls don't cover

AI introduces a new threat surface. The risks below are pulled from the Standard's risk model — and each maps to a control set in the workbook.

OWASP LLM01 · 2025

Prompt Injection

Malicious instructions hidden inside a document, web page, email, ticket, or RAG corpus override the user's intent. Direct (jailbreaks) and indirect (untrusted content) variants. Treat every input as potentially adversarial.

Tracked: HRD-G04 · HRD-M03 · HRD-M11
OWASP LLM02 · 2025

Sensitive Information Disclosure

Pasting customer PII, credentials, IP or proprietary code into AI tools. Even with training disabled, content traverses third-party infrastructure. RAG retrieval that ignores user ACLs leaks data sideways. Default: "treat AI like a public URL".

Tracked: HRD-A02 · HRD-H01 · HRD-M04 · HRD-M06
OWASP LLM03 · 2025

Supply Chain

Compromised model weights, poisoned datasets, malicious connectors / plugins / MCP servers, dependency attacks on the model serving stack. Treat the model and its plugins as third-party code with attestation requirements equal to OS-level dependencies.

Tracked: HRD-B01 · HRD-C01 · HRD-E01 · HRD-L02 · HRD-L06
OWASP LLM04 · 2025

Data and Model Poisoning

Adversarial training data, fine-tune corpora, or RAG sources designed to bias outputs, embed back-doors, or trigger unsafe behaviour on specific inputs. Mitigation: signed datasets, provenance tracking, eval harness for poisoning probes.

Tracked: HRD-L06 · HRD-M02 · HRD-M14
OWASP LLM05 · 2025

Improper Output Handling

Unfiltered LLM output rendered into HTML, executed as SQL, passed to a shell, or trusted as a tool argument — classic XSS / SSRF / command injection enabled by treating model output as trusted. Always validate, escape, and sanitise downstream.

Tracked: HRD-M07 · HRD-M08 · HRD-M09
OWASP LLM06 · 2025

Excessive Agency

Agents inherit the user's permissions. Connectors, plugins, MCP servers and scheduled tasks can act for hours without supervision. The attack scenario is no longer "data disclosed" — it's "workflow executed". Tool allow-lists, argument validation, human-in-the-loop and iteration caps are non-optional.

Tracked: HRD-A04 · HRD-J01 · HRD-M10 · HRD-M11
OWASP LLM07 · 2025

System Prompt Leakage

System prompts often encode policy, secrets, or business logic that the model treats as authoritative. Extraction attacks (jailbreaks, role-play, encoding tricks) reveal them. Treat system prompts as version-controlled, reviewed code; never put real secrets in them.

Tracked: HRD-M05
OWASP LLM08 · 2025

Vector and Embedding Weaknesses

Vector databases that index without ACL boundaries leak via similarity search. Embedding inversion can recover near-original text. Embedding-poisoning attacks plant retrieval traps. Mitigation: per-user ACL indexes, embedding-model + version pinning, daily reconciliation.

Tracked: HRD-M06
OWASP LLM09 · 2025

Misinformation & Hallucination

Models confidently produce wrong facts, citations and code. In high-impact settings — clinical, legal, financial, code that ships to production — unverified output is a safety issue, not a quality issue. Cite-then-summarise, groundedness scoring, human review at decision points.

Tracked: HRD-M07 · HRD-M08 · HRD-M14
OWASP LLM10 · 2025

Unbounded Consumption (Denial-of-Wallet)

Token-by-token billing turns a runaway agent or an abusive user into an instant five-figure cloud bill. Per-tenant rate limits, daily token + cost caps, anomaly detection on call-rate / context-size, hard kill at 100% budget. Pair with LLM06 controls — agent loops are the highest-risk amplifier.

Tracked: HRD-M12
Cross-cutting · NIST MEASURE-2.11 · EU AI Act Art. 10

Bias & Over-Reliance

Not in OWASP LLM Top 10 but unavoidable in regulated estates. Models reflect their training data. Decisions about people — hiring, credit, fraud, healthcare — require documented human oversight, fairness testing, demographic parity / equalised-odds scoring, and the ability to override.

Tracked: HRD-M02 · HRD-M11
